# Answer effects and semantic mapping

Status: proposed design, 29 October 2026. No application behaviour or provider connection was changed. The executable source remains the existing application; this document specifies the intended contract.

The later [onboarding/booking reconciliation](payload-reserve-plan/reconciliation/README.md) corrects the booking-related answer meanings, aliases and effects. Its effective manifest is the build input. Treat the older examples here as source history wherever they conflict, especially mandatory booking, recurring membership, table-system discovery and Kenya timezone setup.

The registry contains 235 taxonomy fields, 25 distinct legacy category keys and 40 new operational questions. Every current taxonomy key has its own typed proposed definition, applicability, source shape, validation and explicit screen effects.

## Resolution order

1. Read canonical taxonomy and selected specialty IDs. A merchant may select several capabilities; historical one-specialty drafts retain their original source.
2. Load raw answers with source version and context. Missing is unknown; no and zero are valid answers.
3. Apply explicit lossless semantic mappings. Preserve the source option label and original value. A broader, ambiguous or conflicting value creates a clarification task.
4. Resolve capability defaults, then explicit specialty, offering, location and resource overrides within their scopes. An override cannot widen permissions or regulated authority.
5. Ask only conditional operational questions needed by the selected workflow. A band is useful context, not an exact scheduling or pricing rule.
6. Compute the display configuration and separate readiness result per capability and location. Configure the draft portal immediately; mark unsupported or unconfirmed actions pending setup.
7. Require valid domain contracts, verification, authoritative sources, platform/operator permissions and connection support before enabling mutations.
8. Version the accepted configuration. Changed answers recompute future work and discovery drafts, with an impact preview; do not rewrite the terms/stages of accepted work.

## Important mappings

| Existing answer | Proposed interpretation | Follow-up and limit |
|---|---|---|
| equipment_provided yes/no | all/some/none coverage | no→none is lossless. yes requires clarification between all and some. The current duplicate namespace must be removed. Ask explicit equipment lists. |
| booking_required or appointment_booking | booking setup request | Ask exact duration, notice, resource model and confirmation authority. A request is not a confirmed reservation. |
| home_service/home_visits/mobile_service | customer-location variant request | Ask service area, travel/resource setup and source support. Do not demand a rider pickup counter for this alone. |
| session_format both / session_location flexible | several service variants | Configure each enabled in-person/digital variant independently. |
| pickup_delivery / collection | incoming leg setup | Ask return mode separately; identify goods custody and proof for both legs. |
| min_order 5000 | KES5000 or more in current source | Keep the open-bound token and ask an exact minimum. It is not automatically an exact KES5000 minimum. |
| pricing_basis per_bag | current label says bag / kg | Ask the exact billing unit and rate. Never silently equate bag with kilogram. |
| advance_booking_hrs, capacity_range, fleet_size and other bands | descriptive timing/resource context | Ask exact operational values before calculating acceptance/capacity. |
| same_day/next_day/half_day/full_day | symbolic local calendar window | Ask cutoff, timezone, operating calendar and precise duration where enforcement needs it. |
| price_per_sqm / price_per_sqft | area rate, explicit unit retained | Ask currency, minor-unit precision, billing period and area basis. |
| liquor_license / regulatory_license / halal_certified | declaration/evidence task | Do not publish verified badges or enable controlled work from the answer alone. |
| reservation_system / POS preference | system discovery | Ask function, vendor/version, scope, supported connection and authority. No API connection is implied. |
| cuisine_types / brands / fragrance / dietary facets | relevant discovery and offering fields | Most attributes do not alter the work state machine. Claims require appropriately qualified publication. |
