# NexG API handoff, 17 November 2026

For whoever keeps building the NexG API at `api.nexgapp.com`. Everything described here is on `main`, deployed, and applied in the production database as of 17 November 2026. The owner sends anything private (keys, accounts, partner details) separately.

**This repository is public, and so are its issues, PRs and commits.** Use placeholders such as `nexg_test_…` in examples. Secrets live only on the server or in Vercel, and never behind a `NEXT_PUBLIC_` prefix.

## What it is

The NexG API lets a merchant's systems, partner apps and NexG's own tools talk to NexG: read the catalogue, book services, and hear about bookings as they change. Later, connectors will translate between NexG and a partner's own system (a POS, ERP or reservations system), so NexG can read availability and create or update bookings there.

- **`apps/api`** is a Next.js 14 app on Vercel (project `nexg-api`). It serves the `/v1` endpoints, the reference and guides under `/docs`, and the developer console at `/developers`.
- **The database decides.** Every rule lives in Supabase Postgres functions: `security definer`, `set search_path = ''`, and granted only to the role that needs them. The route handlers authenticate, check the request's shape and turn database refusals into the JSON error envelope. API keys are stored as SHA-256 hashes; only a short prefix is kept readable.
- **One registry drives the docs.** `apps/api/lib/reference/endpoints.ts` describes every endpoint; the reference pages, sidebar, home page and changelog are built from it. `tests/reference.test.ts` fails when the registry, the route files, the middleware's route table (`lib/routes.ts`) and the changelog (`lib/reference/changelog.ts`) disagree.

## Endpoints today

| Method and path                         | What it does                                                                                                         | Key                                                   |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `GET /v1/catalog/merchants`             | Live merchants, filtered by city, category or search, keyset-paged.                                                  | Optional (`public_read`)                              |
| `GET /v1/catalog/merchants/{id}`        | One merchant, every open branch and its catalogue.                                                                   | Optional                                              |
| `GET /v1/zones`                         | Delivery zones.                                                                                                      | Optional                                              |
| `GET /v1/experiences`                   | Upcoming events.                                                                                                     | Optional                                              |
| `GET /v1/services`                      | The service codes that can be booked (airport transfer, intercity transfer, courier, venue booking).                | Optional                                              |
| `GET /v1/orders`                        | The key's merchant's orders, newest first. A test key reads its test bookings instead.                               | `merchant_read`                                       |
| `GET /v1/orders/{id}`                   | One of those orders.                                                                                                 | `merchant_read`                                       |
| `POST /v1/orders`                       | Book a service. Live key: a real order charged to the merchant's NexG account. Test key: a sandbox booking.          | `merchant_write`, with an `Idempotency-Key` header   |
| `POST /v1/test/orders/{id}/status`      | Sandbox only: move a test booking to a later status.                                                                 | `merchant_write`, test key                           |

There is no `PATCH`, `PUT` or `DELETE` yet. Any other method or path under `/v1` gets a JSON 405 or 404 from the middleware. Every answer uses the same envelope (`ok`, `data` or `error`, `meta`), and every error carries an `X-Request-Id`. A successful answer to a keyed request says `NexG-Environment: live` or `test`.

**Rate limits** are token buckets per key and merchant, 60 tokens a minute by default. An order read costs 3 tokens and a booking 5. Test keys spend from their own bucket.

## Keys

- **Live or test.** A test key starts `nexg_test_`. The key decides where a request goes, so going live means changing the key and nothing else.
- **Scopes:** `public_read`, `merchant_read`, `merchant_write`. A merchant key works only while its merchant may operate: not while it is paused, suspended or delisted, or its application is waiting for approval.
- **Issuing.** In the developer console, by a merchant's owner. The console offers `merchant_write` on test keys only.
- **Revoking.** In three places:
  - the developer console's "Your API keys" card;
  - the merchant's Settings › API & webhooks on nexgapp.com, for the owner;
  - Admin › Settings › API & Webhooks, where any staff member can revoke a key and must give a reason.
- **Revoking rules** (`rpc_api_key_revoke`): staff may revoke any key; the owner may revoke their merchant's keys; whoever issued a key with no merchant may revoke it. Every revoke is audited with who did it.

## The sandbox

- A test key's bookings are `api_test_order` rows with a `TEST-` reference. They never become orders: nothing is dispatched, billed or counted.
- A service NexG has not priced in the merchant's city gets a sample price: KES 1,000 a unit, or once for a flat-priced service.
- **Moving test bookings.** A test booking goes forward only: requested, confirmed, in_progress, completed. It may skip steps, and may be cancelled any time before it is completed. Completed and cancelled are final. There are two ways to move one:
  - the API, `POST /v1/test/orders/{id}/status`;
  - the console's Test bookings card, which also makes sample bookings without code.

## Order events (webhooks)

- **Endpoints.** A merchant's owner adds them in the console, live or test, up to five of each. Each is https on a public host, port 443.
- **Signing.** The signing secret is kept in Supabase Vault and shown once. Each delivery is signed with HMAC-SHA256 over `"<t>.<body>"`.
- **Events:**
  - `booking.created`;
  - `booking.status_changed`, sent only when the shared status changes;
  - `ping`, from the console's Send test event.
- **Statuses.** Every booking has one shared status (`requested`, `confirmed`, `in_progress`, `completed`, `cancelled`). Its `stage` keeps the detail, such as `picked_up`.
- **Delivery.** Events are written to `api_webhook_event` and `api_webhook_delivery`. The pg_cron job `api-webhooks` runs `fn_api_webhook_dispatch` every minute, sending through `pg_net`. A 2xx answer within 10 seconds counts as delivered. Anything else is retried after 1 minute, 5, 30, 2 hours, 6, 12 and 24, then marked failed.
- **Testing.** A webhook.site address is fine for test endpoints, never for live ones.

**How migrations reach production.** CI checks that every migration applies from zero, but nothing applies them to production automatically, and every push to `main` deploys the apps at once. So:

- Apply a database change by hand, with the owner's go-ahead, before pushing code that needs it.
- Keep each change backward-compatible with the code already live.
- Before applying, compare each function the migration replaces with production's body. After applying, check the new bodies, grants and `fn_wiring_check()`, then record the history row.

## Running and testing

- **Run it locally:** `pnpm --filter @nexg/api dev` serves on `http://localhost:3002`. It needs `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` and the server-only `SUPABASE_SERVICE_ROLE_KEY` for a local Supabase stack. Sign-in uses Cloudflare Turnstile when `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is set; against a local stack it can stay unset.
- **App checks:** `pnpm --filter @nexg/api test`, `typecheck` and `lint`. Run Prettier on every file you change.
- **Database checks:** `supabase test db` on a local stack.
- **Generated types:** after a migration that adds or changes functions, run `pnpm db:types`. CI fails when the committed types are stale.
- **The whole sandbox flow by hand:**
  1. Issue a test key in the console.
  2. Add a test webhook endpoint.
  3. Book with `POST /v1/orders`, adding an `Idempotency-Key` header.
  4. Move the booking with `POST /v1/test/orders/{id}/status`, or use the console's Test bookings card.
  5. Watch the events arrive at the endpoint.

**Adding an endpoint:**
1. Write the route file under `app/v1`.
2. Add it to `lib/routes.ts`.
3. Add an entry with status `live` to `lib/reference/endpoints.ts`.
4. Add an `added` changelog entry naming its slug.
5. Write the tests.

`tests/reference.test.ts` fails until all of these agree. Don't export anything from a route file except the HTTP methods and Next's route settings.

## Waiting on the owner

1. **Who may book for real, charged to their NexG account.** Booking with a live key (`merchant_write`) is credit to merchants. The choice is between any approved merchant (self-serve) and only merchants NexG enables. The console doesn't offer live booking keys, but `fn_api_key_issue` still lets an owner create one directly, so a real gate needs a database change once this is decided.
2. **Service prices for each city** (`fees.service.*` settings). None are set, so every live booking is refused with "That service is not priced yet".
3. **Two settings on the API project in Vercel** (the booking engine's address and a new restricted key for it). These unlock phase 2. The owner sets them, not code.
4. **Phase 4:** may partners such as travel agents book other merchants' offerings? What is the cancellation policy?
5. **Phase 5:** who pays by M-Pesa or card, the merchant or their guest?
6. **Connectors to merchants' own POS or ERP systems:** paused.
   - Decided: pull products, prices, stock and till sales; the merchant's own system is the master copy.
   - Open: which systems come first.

**Smaller gaps:**

- **Console sign-in is password only.** A merchant who joined with an email code or Google needs "Forgot password" on nexgapp.com first.
- **Admin can't see merchants' webhook endpoints or failed deliveries.**
- **Webhooks lack:**
  - a resend button;
  - signing-secret rotation;
  - automatic switch-off for an endpoint that keeps failing;
  - payment events.
- **Keys lack** a usage view for developers, a default expiry and a rotation flow.
- **Webhook addresses** are checked by name; there is no extra guard against a public name that points to an internal address.
- **No "Sign in with NexG"** for third-party apps.
